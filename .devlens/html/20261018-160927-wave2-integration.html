5. Open issues

Shared Postgres crash-recovery during the PC-HD-08 probe. At 16:00:09–10, at the end of a 60 s probe with 48 concurrent DB reads (8 dev users), the API logged "unexpected EOF" and then FATAL: the database system is in recovery mode. That Postgres runs on the staging host and also serves the staging app DB, so this probably meant about 1–2 s of unavailability for staging. It recovered on its own, migrate status was fine afterwards and there were no errors after 16:01. The staging host was not inspected (off-limits). Please check its Postgres log and OOM-killer messages. No further concurrent load was sent.
  • Shared request pool under load: during the same probe user reads timed out at 10 s through the tunnel, and the worker's /internal/v1/workers/*/heartbeat|status calls got 500/503. Workload endpoints should get a reserved pool or priority (follow-up for platform-core). /readyz itself stayed 200 throughout (p99 1.6 ms).
  • Memory: the 50-route overload peaks at 580 MB RSS for a 512 MiB GOMEMLIMIT (heap 515 MB, ~13 % over). A hard 512 MiB cgroup could OOM-kill it; no cgroup was available here to test. Options: budget ≤ 40 % for heavy fan-out, a lower detach threshold, or charge fetch buffers to the budget.
  • Stress spread is large (±20–30 %) on this VM and the host disk degraded in the afternoon. The final build's throughput was therefore not measured cleanly: the clean-window numbers come from builds with the merged code ± the controller fixes, and the memory-path fixes were costed by microbenchmark (detach 0.9 µs per 1 KB record, only under budget pressure). Re-run S2/S5 on a quiet host before quoting final numbers.
  • S3 deploy→running p95 rose from 32.5 to 48 s at 1000 routes (p99 244 → 307 ms). Not investigated.
  • The Go test loadgen TestProduceThenMeasureIsComplete and the runner chaos test are load-sensitive: each failed once under full-suite load and passes in isolation.
  • Still open in the plans: PE-LK-30 lookup batching, PE-FC-61..63, CN-LS-20 cross-team lookup sources, JS-PA-41 filter+steps+JS (only JS-only was re-run).

6. Decisions in this step

  • F4 × F9: kept F4's compile-time projection.Recorder; F9's step.FieldAccessor declaration now feeds it, and lookup stays path-bounded.
  • Auto in-flight invariant: never below the start limit without memory pressure, so auto can't do worse than the old fixed default.
  • Memory budget: detach records once the budget is filling instead of always, keeping franz-go zero-copy on the fast path; size fetches from the budget.
  • Migration 2100_dlq_workflow renumbered to 3100_dlq_workflow (P4 range, dead-letters block).
